# Authentication — PixelVault

---

## 1. Overview

PixelVault uses a **two-layer authentication model**:

1. **JWT Bearer Token** — proves who the user is for every API call.
2. **Master Password** — a separate secret required to decrypt vault/notes data. It is never stored.

---

## 2. User Registration Flow

```
Client → POST /register { username, email, password }
  → Pydantic validation (schemas.UserCreate)
    → min 8 chars, uppercase, lowercase, digit, special char
  → DB check: username and email uniqueness
  → bcrypt.hashpw(password, bcrypt.gensalt()) → hashed_password
  → Store User row
  → Return UserOut (no token issued — user must log in separately)
```

---

## 3. Login Flow

```
Client → POST /login (OAuth2PasswordRequestForm: username, password)
  → login_limiter.check(username) → raise 429 if locked out
  → DB query: User by username
  → bcrypt.checkpw(password, user.hashed_password)
    → Fail: login_limiter.record_failure(username) → raise 401
    → Pass: login_limiter.reset(username)
  → auth.create_access_token({"sub": username}, expires=30min)
    → JWT signed with SECRET_KEY (HS256)
  → Return {access_token, token_type: "bearer"}

Client (auth-service.js)
  → SessionManager.saveSession(token, username, raw_password)
    → sessionStorage: token, username, encryptionKey (= raw master password), sessionExpiry
    → Clears any stale localStorage entries
  → window.location.href = "dashboard.html"
```

---

## 4. Request Authorization

Every protected endpoint uses:
```python
current_user: models.User = Depends(auth.get_current_user)
```

`get_current_user` implementation:
```
Extract token from Authorization: Bearer header
  → jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
  → Extract "sub" claim (username)
  → DB query: User by username
  → Return User object (or raise 401)
```

`api.js` automatically injects the header for every request:
```javascript
options.headers['Authorization'] = `Bearer ${session.token}`
```
401 responses automatically clear the session and redirect to `index.html`.

---

## 5. Session Management (Frontend)

Implemented in `session-manager.js`:

| Key | Value stored | Notes |
|---|---|---|
| `token` | JWT access token | Used in Authorization header |
| `username` | Plain username | Display purposes |
| `encryptionKey` | **Raw master password** | Sent as `master_password` to vault/notes endpoints |
| `sessionExpiry` | Unix timestamp (ms) | 30 minutes, slides on each `getSession()` call |

**Security properties of sessionStorage:**
- Tab-scoped: cleared when the browser tab/window is closed.
- Not accessible from other tabs or windows.
- Not persisted to disk (unlike localStorage).
- Still accessible to JavaScript on the same origin.

---

## 6. Route Guard

`auth-service.js` runs `AuthService.checkAuth()` on every page load:

```
checkAuth()
  → SessionManager.getSession()
    → null (no session / expired):
        if not on index.html → redirect to index.html
    → valid session:
        if on index.html → redirect to dashboard.html
```

This runs before any page-specific logic executes, enforcing protection on all non-index pages.

---

## 7. Logout

```
AuthService.logout()
  → SessionManager.clearSession()
    → Removes: token, username, encryptionKey, sessionExpiry from sessionStorage
    → Also removes: token, username from localStorage (legacy cleanup)
  → window.location.href = "index.html"
```

---

## 8. Rate Limiting

Implemented in `main.py` as an **in-memory** `RateLimiter` class.

| Limiter | Key | Limit | Window | Applied to |
|---|---|---|---|---|
| `login_limiter` | username | 5 failures | 15 min | `POST /login` |
| `master_pwd_limiter` | user ID (str) | 5 failures | 15 min | `/vault/list`, `/vault/audit`, `/vault/export`, `/notes/list` |

**Limitation:** In-memory only — resets on server restart. Not suitable for multi-process or distributed deployments.

---

## 9. JWT Configuration

| Parameter | Value |
|---|---|
| Algorithm | HS256 |
| Expiry | 30 minutes |
| Claim | `sub` (username) |
| Secret source | `.env` → `SECRET_KEY`, or random `secrets.token_hex(32)` at startup |

> **Warning:** If `SECRET_KEY` is not set in `.env`, a new random key is generated every server restart. All existing tokens are immediately invalidated.

---

## 10. Password Hashing

- Library: `bcrypt` (v4.0.1) called directly (not via passlib)
- Salt: auto-generated by `bcrypt.gensalt()`
- Stored: `hashed_password` column in `users` table
- Verification: `bcrypt.checkpw(plain.encode(), hashed.encode())`
- Truncation risk: bcrypt silently truncates at 72 bytes — passwords longer than 72 characters have reduced entropy.
